# Measurement checklist

What to measure after this branch, and how to read it. Commands and SQL live in [performance-measurement.md](performance-measurement.md). This file does not replace that one.

Nothing below is a measured result. The result column is empty on purpose. Do not copy an example into it.

Baseline commit: `529e2a1bd866d60c772e8e2e9ac3182388318d94` (`origin/main` when this branch was cut). Record the fixed commit with `git rev-parse HEAD` on this branch.

## What this PR changed

- **`/match` N+1, `match_jobs`.** One `IN (...)` query loads cached `MatchAnalysis` rows. Missing KO/EN analyses run together under `asyncio.gather` and `llm_semaphore` (8). One `add_all` and one commit writes them. Expected effect: a cold match no longer does one select and one commit per top job, and the analysis calls overlap instead of running one after another.
- **`/match` connection release, `match_jobs`.** `commit` before the rerank call and again before the analysis calls. Expected effect: the request does not hold a pool connection across those OpenAI calls. `expire_on_commit` is already false, so the loaded rows stay usable.
- **`/match` cache write, `match_jobs`.** `setex` is inside `try/except`. Expected effect: a Redis write error is logged and the JSON response is still returned.
- **Crawler N+1, `store_scraped_jobs` (called from `scheduled_north_america_crawl`).** One `(title, company)` select per city, bounded metadata and embedding calls, then one `add_all` / commit. A bad job is skipped. If the batch commit fails, each row is retried on its own. Expected effect: queries per city stay flat as the number of postings grows. Dedup is still title + company, first row in the batch wins.
- **HNSW query shape, `nearest_postings_stmt`.** `ORDER BY embedding <=> :vec LIMIT 100`. The selected score is still `1 - distance`. Expected effect: the nearest-neighbour step is eligible for `ix_job_postings_embedding_hnsw`. The JSON keys are unchanged. Which rows come back can differ, because the scan is approximate.
- **HNSW session settings, `configure_hnsw_scan`.** For that transaction only: `SET LOCAL hnsw.ef_search = 100`. When `vector_extension_supports_iterative_scan` sees pgvector >= 0.8, also `SET LOCAL hnsw.iterative_scan = strict_order`. Expected effect: the scan is allowed to return 100 neighbours (the server default of `ef_search` is 40). On 0.8+, filters are applied while the scan continues, in distance order.
- **Index on existing databases, `lifespan` / `HNSW_INDEX_SQL`.** After `create_all`, startup runs `CREATE INDEX IF NOT EXISTS ix_job_postings_embedding_hnsw ... USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)`. Expected effect: a database created before the model had this index gets it. `create_all` does not add indexes to a table that already exists. If an index of that name is already there, the statement does nothing.
- **Opt-in measurement only.** `QUERY_STATS` (`app/database.py`, cursor hooks and the HTTP middleware) and `MATCH_TIMING` (`_Timer` in `match_jobs`). Both off unless set to `1`. Expected effect: no response change when they are unset. When set, a log line and, for `MATCH_TIMING`, a `Server-Timing` header.

The Redis key is unchanged: `match_results:{resume_id}:{md5 of the filter lists}` for one hour.

## Filter-then-index vs index-then-filter

This is inferred from the SQL the code builds. It is not an `EXPLAIN` result. Treat the "before" plan as a hypothesis until `EXPLAIN` on `529e2a1` confirms it.

**Before.** `match_jobs` on the baseline orders by a labeled `1 - (embedding <=> :vec)` (`desc("score")`), with the location, level, type, and `skills ILIKE` filters in the same statement. `<=>` is what `vector_cosine_ops` indexes. An `ORDER BY` of `1 - distance` is not that operator, so `ix_job_postings_embedding_hnsw` is not eligible. The planner then has to filter first (the `WHERE` clause, possibly with the btree indexes on `location`, `experience_level`, and `employment_type`) and exact-sort the survivors by the score expression. On a table of this shape that is usually a `Seq Scan` plus a `Sort`. Confirm with `EXPLAIN` before stating it as fact. `skills ILIKE '%…%'` cannot use a btree index.

**After.** `nearest_postings_stmt` orders by `embedding <=> :vec` and limits to 100. The resume embedding is loaded in an earlier statement and bound as a parameter. The index, when the planner picks it, runs first and produces neighbours. The `WHERE` filters then drop some of those neighbours (index, then filter).

What limits the candidate list:

- `hnsw.ef_search` is the width of the HNSW search. The server default is 40, which cannot fill `LIMIT 100`. This branch sets it to 100 for the `/match` transaction only. `SHOW hnsw.ef_search` in another session still shows the server default.
- On pgvector >= 0.8, `hnsw.iterative_scan = strict_order` keeps walking the index, in order, until 100 rows also pass the filters.
- On older pgvector that setting does not exist. One index pass is filtered afterwards. A selective location, level, type, or skill filter can return fewer than 100 rows. The code does not raise `ef_search` above 100 and does not oversample. The rerank then sees a shorter list. The HTTP body is still at most 10 jobs, so a short candidate list does not show up as a short JSON array. Count the SQL result, not `len` of the `/match` response.

A small table often still gets a `Seq Scan` even when the query is eligible. That is the planner choosing a cheap exact plan. It is not proof the index cannot be used. `SET enable_seqscan = off` is only a capability check. Turn it back on before any timing run.

## How to run it fairly

Use one machine for the baseline checkout and this branch. Same Postgres, same Redis, same `job_postings` contents, same resume id and the same filter query string. Do not mix a cold `/match` into a warm average.

1. Record `git rev-parse HEAD` for each checkout. The baseline sha to start from is `529e2a1bd866d60c772e8e2e9ac3182388318d94`.
2. Warm up: one unrecorded `/match` (or one unrecorded Locust minute) so pools and imports are loaded. For a cold-path measurement, flush that resume's Redis key afterwards (`redis-cli DEL` of the `match_results:{id}:...` key) and delete its `match_analyses` rows if the cold path is what you are timing. For a warm-path measurement, leave them.
3. Repeat each configuration 3 times. Interleave: baseline, fix, baseline, fix, baseline, fix. A single run is not a comparison.
4. Reset `pg_stat_statements` before each counted request. Restart is not required between repeats if the process env (`QUERY_STATS`, `MATCH_TIMING`) is unchanged.
5. Write the result column above, and the table below, from those runs. Leave a cell blank rather than guessing.
